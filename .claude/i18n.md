# i18n Architecture

## Overview

Two locales: **`es`** (the `defaultLocale`) and **`en`**.
Stack: **`next-intl`** (v4). There is no i18next in this project.

`es` is the default because the Dominican market is the primary audience — English is the
secondary, expat/international locale. This is why `x-default` points at `/es` in the sitemap and
why the bare `/` resolves to Spanish for clients that express no preference. Both are deliberate.

All public routes are locale-prefixed (`localePrefix: "always"`), and the URL segments themselves
are localised: `/en/contact` ↔ `/es/contacto`, `/en/pricing` ↔ `/es/precios`.

## Localised Pathnames

`routing.pathnames` maps **internal app-router folder names → per-locale external slugs**:

```ts
"/about-me": { en: "/about-me", es: "/sobre-mi" },
"/contact":  { en: "/contact",  es: "/contacto" },
"/blog":     "/blog",                     // identical in both locales
```

- The **KEY is the folder name under `src/app/(root)/[lang]/`. Never rename those folders** — the
  key is what the rest of the codebase references.
- next-intl localises the path prefix, but **not** the `[slug]` token. Per-locale slug _values_
  come from `src/lib/slugs.ts` (`slugForLocale`, `slugPair`), which read `slug` / `slugEs` off the
  Sanity doc.

## Locale Detection (Middleware)

`src/middleware.ts`. The matcher excludes `/api`, `_next`, `/studio`, and the generated static
files (`sitemap.xml`, `robots.txt`, `llms.txt`, `llms-full.txt`, `llms-full-es.txt`,
`indexnow-key.txt`, the Google verification file) so the locale rewrite doesn't turn
`/llms.txt` into `/en/llms.txt`.

For the bare `/` there are two distinct paths, and **the difference is intentional**:

| Request to `/`                                                                            | Response                              |
| ----------------------------------------------------------------------------------------- | ------------------------------------- |
| No `NEXT_LOCALE` cookie **and** absent/wildcard `Accept-Language` (the crawler signature) | **308** → `/${defaultLocale}` (`/es`) |
| Anything else (real browsers send a concrete `Accept-Language`)                           | **307** → negotiated locale           |

`Vary: Accept-Language, Cookie` is set on both, so caches key correctly.

The 308 is a _cacheable, permanent_ redirect that consolidates crawl budget and link equity onto a
single URL, instead of re-running next-intl's uncacheable 307 on every crawl. **This is not a bug.**
The 2026-08-24 SEO re-audit initially flagged it as a high-severity defect before the middleware
comment was read; it was withdrawn. Do not "fix" it without revisiting that decision.

`localeDetection` is left at its default (`true`), so un-prefixed URLs follow the visitor's
browser/cookie preference.

## Server Components

```ts
import { getTranslations } from "next-intl/server"

export default async function MyPage() {
  const t = await getTranslations()
  return <h1>{t("hero.title")}</h1>
}
```

The locale comes from the request context — you do not pass `lang` in. Pages that need the raw
locale string still read it from `params`.

## Client Components

`NextIntlClientProvider` wraps the client tree in `src/app/(root)/[lang]/layout.tsx`.

```tsx
"use client"
import { useTranslations, useLocale } from "next-intl"

export function MyButton() {
  const t = useTranslations()
  const locale = useLocale()
  return <button>{t("common.submit")}</button>
}
```

For internal links and Sanity-driven hrefs, prefer the project wrapper — it resolves localised
paths and per-locale slugs for you:

```tsx
"use client"
import { useLocale } from "@/i18n/useLocale"

const { t, currentLocale, getLocalizedPath, getServiceHref, getBlogHref } =
  useLocale()
```

Use `Link` from `src/i18n/navigation.ts` (not `next/link`) so the locale prefix and localised
pathname are applied automatically.

## hreflang & Canonicals

`routing.ts` sets **`alternateLinks: false`**, disabling next-intl's automatic hreflang `Link`
HTTP header. Its `x-default` pointed at un-prefixed URLs (`/`, `/blog`) which 307-redirect, and
crawlers flag "hreflang to redirect / non-canonical".

Instead we emit our own on-page `<link rel="alternate">` tags via `buildAlternates()`
(`src/lib/urls.ts`), used from each page's `generateMetadata()`. `src/app/sitemap.ts` emits the
matching `xhtml:link` alternates, with `x-default` → the default locale (`/es`).

## Sanity Localised Fields

Localised Sanity fields are plain objects (the Sanity i18n plugin is not used):

```json
{ "en": "Hello", "es": "Hola" }
```

```ts
const { lang } = await params
const data = await client.fetch(...)
return <h1>{data.title[lang]}</h1>
```

Document **slugs** are the exception — they live in two fields, `slug` (en) and `slugEs` (es), and
are resolved via `src/lib/slugs.ts`.

## Adding a New Translation Key

1. Add the key to `src/i18n/locales/en/translation.json`.
2. Add the translated value to `src/i18n/locales/es/translation.json`.
3. Use `t("your.key")` in the component.

Update both files together. A missing key renders **the key itself**, silently — no thrown error
and no console warning (`getMessageFallback` / `onError` in `src/i18n/request.ts`), so a missing
translation will not fail a build or a test. Check visually.

---

## Adding a New Locale

1. Add the code to `locales` in `src/i18n/routing.ts`.
2. Add a per-locale entry to every route in the `pathnames` map in the same file.
3. Create `src/i18n/locales/<code>/translation.json` with all keys translated.
4. Add the matching slug field to any Sanity schema that has `slug` / `slugEs`, and extend
   `src/lib/slugs.ts`.
5. Confirm `src/app/sitemap.ts` picks the locale up — it iterates `routing.locales`, so it should
   need no change.
6. Verify hreflang output from `buildAlternates()` and the `x-default` target.
